# HACA 项目分支维护及共性回流指南（面向项目分支维护负责人）

## 背景

HACA 是通用脚手架：内置按「需求澄清 → 方案设计与风险识别 → 子任务拆分 → 按序实现与提交」工作的 HACA Agent，在 **Human-in-the-loop** 模式下**每步结束须经人工确认后再进入下一步**，不会自动跨步。各阶段配套 skills（含 superpowers）对应各步的产出与执行方式，构建阶段还衔接 TDD、证据门禁、提交与复检等质量要求，使协作在**可核验的产出与统一流程**下推进。

HACA 把仓库里的相关配置拆成 **治理层、编排层、技能层** 三层（分层定义与边界见《[HACA 执行流程详细描述](haca-execution-flow.md)》第 2 节）：**各层各司其职，同一类约束不得在多层重复书写**。落地这三层后即可沿用统一人机协作路径，而不必从零自拟一套流程与规则。

各项目常需在**技能层**做本地化扩展，例如：让 Agent 掌握本仓库依赖与构建方式、沉淀项目规则与最佳实践、定制检查/生成/提交流程等。若把这些全部堆进公共 `develop`，易混入项目私货，因此需要：**从 `develop` 拉出项目维护分支，在分支上增强；可跨项目复用的改进再提回 `develop`，供全公司共享。**

---

## 三层架构

做分支维护与回流判断时，先分清改动落在**治理层**、**编排层**还是**技能层**。三层职责边界如下表（摘自《HACA 执行流程详细描述》§2）：

| 层级 | 职责 |
|------|------|
| **治理层** | 全局约束与禁止项；不包含命令级执行顺序或步骤内操作细节 |
| **编排层** | Agent 人格、命令入口、步骤识别表、Build Loop 流程、异常处理 |
| **技能层** | 各步骤的具体执行规程、输出格式、内部判定逻辑（各 `SKILL.md`） |

**输入模板**（**不属于三层中的独立一层**，与《HACA 执行流程详细描述》§1「输入模板」一致）：`.github/prompts/haca-step*.prompt.md` 仅作各步入口文案模板，**不包含**编排逻辑、门禁规则或提交策略；须引用**治理层**与**技能层**为唯一事实来源（见《HACA 执行流程详细描述》§2）。

### 治理层

- **管什么**：仓库级「什么允许、什么禁止」——与《HACA 执行流程详细描述》中**治理层**定义一致。
- **怎么动**：若要调整，与研发管理办公室协商。
- **以 `.github` 为例（主编辑源）**：
  - `.github/copilot-instructions.md`：仓库级治理约束（仅定义允许与禁止；不含命令级执行顺序或步骤内细节）。

### 编排层

- **管什么**：HACA Agent 如何被调用与如何串步骤——人格、命令、步骤识别、Build Loop 流程、异常处理等。
- **怎么动**：牵动全局人机流程与入口，若要调整，与研发管理办公室协商。
- **以 `.github` 为例（主编辑源）**：
  - `.github/agents/haca.agent.md`：HACA Agent 定义（与**编排层**职责一致）；步骤内可执行规程仍以对应 `SKILL.md` 为准。

### 技能层

- **管什么**：各步骤与工具的可执行规程——各 `SKILL.md`、脚本及技能内资源；含 HACA 四步与门禁、提交相关技能包，以及 `superpowers` 等。
- **怎么动**：项目特有增强主要落在此层；在项目分支上改，可复用部分再回流 `develop`。
- **以 `.github` 为例（主编辑源）**：
  - `.github/skills/**`：全部技能内容；项目新增技能也放在此树下。
- **注意**：若对技能的修改会改变**步骤语义、门禁或提交策略**（而不仅是项目域知识），仍应与研发管理办公室对齐。

## 我有一个改动想法，怎么走？

```
[我有一个改进想法]
    ↓
[主要动的是技能层吗？]（不动治理层约束与编排层流程）
    ├─ 否 → 与研发管理办公室商议治理层 / 编排层变更
    └─ 是 ↓
[项目分支维护负责人确认可跨项目复用？]
    ├─ 否 → 只在项目分支做本地技能扩展
    └─ 是 → 提交到 develop，并合并回项目分支
```

## 多平台配置：以 `.github` 为主

HACA 在 GitHub / Cursor / OpenCode 等多套目录下都有对应文件。**主编辑源只有一处：`.github/`**，覆盖治理层、编排层、技能层及 prompts 等受管路径（与 [scripts/README.md](../scripts/README.md) 所列主编辑源一致；若仓库另有 `.github/scripts/` 亦同）。**凡改动上述主编辑源中的文件**，都应先在 `.github` 中修改并运行同步脚本，将内容**派发到 `.cursor/` 与 `.opencode/`**，勿在三个位置各改一份导致漂移。

同步命令、受管路径与校验说明见：[scripts/README.md](../scripts/README.md)。
